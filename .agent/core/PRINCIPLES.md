# Інженерні принципи

- Зберігай коректну поведінку та наявні контракти поза погодженою зміною.
- Виправляй причину проблеми мінімально достатнім способом. Дотримуйся існуючих
  перевірених підходів; нова абстракція потребує конкретної потреби задачі.
- Використовуй зрозумілі назви, явні побічні ефекти та просту структуру.
  Коментар має пояснювати причину або обмеження, які не видно з коду.
- Стиль застосовуй до нового та необхідно зміненого коду. Наявні довгі функції,
  вкладеність або форматування не є дозволом на побічний рефакторинг.
- Числові межі, інструменти форматування, формат міграцій та винятки задає
  [стиль проєкту](../project/CODE_STYLE.md), якщо вони потрібні цьому репозиторію.
- Не додавай залежність, не переписуй модуль і не змінюй публічний інтерфейс без потреби
  погодженої задачі. Для необхідної несумісної зміни узгодь очікувану поведінку.
- Перевіряй спостережувану поведінку й суттєві крайні випадки. Вибір перевірок визначають
  ризик, змінений контракт та критерії, а не сама наявність директорії `tests/`.
