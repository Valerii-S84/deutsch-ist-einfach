# Межі задачі

- Мета = запит користувача, його обмеження та необхідні пов'язані кроки до результату.
  Не додавай незалежну мету, побічний ремонт, нову залежність або документ «про всяк випадок».
- Визнач намір із поточного запиту та контексту. Доручення виконати роботу дозволяє
  необхідні звичайні локальні кроки; не підміняй виконання обіцянкою чи планом.
- Якщо запит лише на аналіз, план або огляд — не змінюй файли. У дорученій реалізації
  аналіз, зміни та перевірка є етапами однієї задачі й не потребують окремих режимів дозволу.
- Перед складною роботою коротко назви результат, межі змін, суттєвий ризик і перевірку.
  Для простої задачі достатньо одного речення; окремий файл плану не потрібен.
- Не вимагай точного списку всіх файлів до необхідного дослідження. Додавай пов'язані файли,
  коли виявлена залежність потрібна для мети; кількість файлів сама по собі не означає зміну мети.
- Звичайний технічний вибір роби за наявними правилами та перевіреними прикладами.
  Припущення, яке впливає на результат, назви явно. Питай про невідомий намір або суттєві
  альтернативи, які неможливо вирішити з доступного контексту; не вигадуй рішення власника.
- Чіткий дозвіл оцінюй за змістом і конкретною дією, а не словником дозволених відповідей.
  Дозвіл зберігається для погодженої дії, доки його не відкликано або не змінилися суттєві умови.
  Нова ризикова дія підпорядковується [правилам безпеки](SECURITY_RULES.md).
- Перед потрібним підтвердженням підготуй доступну дозволену частину та конкретний результат
  для рішення. Не повторюй питання про вже дозволене.
- Побічну знахідку не виправляй. Зазнач її коротко, якщо вона критична або впливає на мету;
  не створюй автоматично новий список покращень.
- Нове повідомлення зазвичай уточнює активну задачу. Відповівши на питання про стан,
  продовжуй її; змінюй мету лише за явного перенаправлення користувачем.
