# Статистика deutschmit.de: спрощений покроковий план

Дата: 2026-09-08. Статус: **план реалізації; код, БД і production ще не змінювалися в межах цього плану**.

Мета — бачити відвідування сайту, шлях окремої сесії, важливі кліки та результати форм. Обсяг: один Admin Hub, один analytics service, одна окрема PostgreSQL і шість сторінок статистики. Перший корисний результат — **Overview + Sessions після кроку 5**. Решта чотири сторінки додаються наступним кроком із тих самих даних.

Цей документ замінює широкий implementation plan із наданого аудиту в частині нової Website Analytics. Чинні вимоги [адміністративного контролю](admin-restoration.md) та [контракти наявної статистики](statistics-contract.md) зберігаються. Кроки нижче — майбутня робота, а критерії «готово» — умови її приймання, не звіт про виконані тести.

## 1. Межі першої версії

| Робимо у v1 | Залишаємо поза v1 |
|---|---|
| Приватний Admin → вибір продукту → окреме меню | Нову систему користувачів, RBAC, MFA або заміну чинної авторизації |
| Окремий TypeScript analytics service: приймання та читання в одному процесі | Окремі collector/query процеси, worker, Redis, Kafka, серверні черги й outbox |
| Окремий PostgreSQL-контейнер, БД, користувач і volume для аналітики | Перенесення контактів або БД Quiz Arena |
| Одна таблиця подій; звіти звичайними SQL-запитами | Таблиці sessions/visitors/jobs, денні агрегати, RLS, партиціювання |
| Рівно 15 типів подій із таблиці нижче | Події кожної відповіді quiz, кожного поля/кроку форми, Web Vitals, пошук |
| Overview, Sessions, Pages, Clicks/Events, Traffic, Conversions | Окремі Visitors, User Flow/Sankey, Performance, Devices, Live, конструктор Funnels |
| Згода, відкликання, дозволені поля, просте очищення даних | Privacy jobs, окрему privacy-панель, replay, heatmaps, keylogging, fingerprinting |
| Збереження доступу до чинної статистики всіх продуктів | Підключення нових ботів і перенесення legacy-історії Quiz Arena |

Існуючі 2FA та права Quiz Arena залишаються чинними. Deutsch Trainer і Shorts Blocker Kids залишаються в picker зі своїми назвами та станом «джерело не підключено». Shorts Blocker Kids у поточному реєстрі — сайт. Відсутність даних не показуємо як нульову активність.

## 2. Проста схема

```text
Website після згоди
  → POST /api/public/analytics/events у Next.js
  → Analytics service → окрема Analytics PostgreSQL

Admin → чинна серверна авторизація → Next.js Admin API
  → той самий Analytics service → та сама Analytics PostgreSQL

Contact API → збереження заявки у чинній БД сайту
  → одна обмежена за часом спроба надіслати form_success в Analytics

Admin → чинний адаптер Quiz Arena → чинний backend і БД Quiz Arena
```

Analytics service розміщується в `services/analytics/` у цьому репозиторії, має власні build, Dockerfile і міграції. Спільна схема подій — один модуль `lib/analytics/contract.ts`, який включають збірки сайту й сервісу. Окрему платформу пакетів або публічний SDK не створюємо.

Додаємо до Compose лише `analytics` та `analytics-db`. Caddy продовжує спрямовувати HTTP до Next.js: окремий зовнішній analytics-домен і нові правила Caddy не потрібні. БД та HTTP-порт сервісу не публікуються назовні. Нові боти зможуть отримати окреме джерело пізніше; зараз сервіс приймає тільки продукт `deutschmit`.

Новий tracking не пише в `contact_requests`, стару `website_analytics_events` або Quiz Arena. Analytics service не отримує доступу до цих БД. Сайт не залежить від готовності analytics при запуску, рендерингу та навігації.

## 3. Порядок виконання

Кожен крок — окрема перевірювана зміна. До залежного кроку переходимо після його критерію «готово»; нове погодження кожної локальної правки не потрібне в межах дорученої реалізації. Перевірки пишемо разом із відповідним кодом. Крок 7 перевіряє цілісність системи.

| Крок | Вхідна умова | Конкретний результат | Межа |
|---|---|---|---|
| 1 | Поточна адмінка | Вибір продукту після входу | Навігація й збереження доступу |
| 2 | Крок 1 | Analytics API + окрема БД + контракт | Синтетична подія зберігається і читається |
| 3 | Крок 2 | Згода, доставка, сесії, перегляди, Telegram-кліки | Реальні дії браузера доходять до нової БД |
| 4 | Крок 3 | Повне покриття 15 подій | Важливі дії сайту потрапляють у сесію |
| 5 | Крок 4 | Overview + Sessions із timeline | **Ядро готове до використання на стенді** |
| 6 | Крок 5 | Pages, Clicks/Events, Traffic, Conversions | Шість сторінок v1; без нового збору даних |
| 7 | Крок 6 | Наскрізна перевірка і готовий порядок перемикання | Локальне приймання v1 |
| 8 | Крок 7 та дозвіл на конкретне розгортання | Перевірений запуск на сайті | Статистика доступна власнику у production |

### Крок 1. Зробити Admin product picker

**Робимо:**

1. Перед зміною зафіксувати доступні маршрути: Website dashboard, заявки сайту й їхній legacy-архів; Quiz Arena dashboard/users/content/economy/promo/system, його login/2FA та адміністративні дії. Використати чинний `admin-restoration.md`, не повторювати повний аудит backend.
2. Створити захищений `/admin/products`; `/admin` і успішний login спрямувати сюди. Джерело карток — чинний `lib/admin-products.ts`.
3. Додати зрозумілий перехід між продуктами. Меню Quiz Arena та його адаптер зберегти. Website поки відкриває чинну статистику й заявки.

**Файли:** `lib/admin-products.ts`, `app/(admin)/admin/page.tsx`, `app/(admin)/admin/login/page.tsx`, `app/(admin)/admin/(secure)/layout.tsx`; новий `app/(admin)/admin/(secure)/products/page.tsx` і невеликий компонент перемикання.

**Не входить:** редизайн усієї адмінки, нова авторизація, зміна API чи формул Quiz Arena.

**Готово, коли:** login → picker → кожен продукт працює; невідомий продукт дає 404; прямий вхід у захищені сторінки й API без сесії закритий; чинні розділи статистики та заявок доступні. Вимкнений backend бота не блокує picker і Website.

### Крок 2. Підняти мінімальні Analytics API та БД

**Робимо:**

1. Закодувати контракт із розділу 4: 15 назв, типізовані дозволені поля, версія, IDs, час, обмеження payload.
2. Створити один сервіс і одну таблицю `analytics_events`. Мінімальні колонки: `product_id`, `event_id`, `event_name`, `schema_version`, `source`, `visitor_id`, `session_id`, `page_view_id`, `sequence`, `occurred_at`, `received_at`, `path`, `metadata` JSONB.
3. Додати `UNIQUE(product_id, event_id)` і три індекси: `(product_id, occurred_at)`, `(product_id, session_id, occurred_at)`, `(product_id, event_name, occurred_at)`. Інші індекси — лише за результатом конкретного повільного запиту.
4. Реалізувати внутрішні маршрути приймання browser/server подій, healthcheck і читання подій однієї сесії. Успішна відповідь на приймання — тільки після commit. Повтор того самого `event_id` успішний, але не створює новий рядок. Невалідний batch відхиляється цілком із 400, без часткового запису.
5. Next.js передає серверний ключ у приватний сервіс. Публічний шлюз дозволяє тільки браузерні події й жорстко задає `deutschmit`; `form_success` приймає лише окремий внутрішній серверний маршрут. Admin API перевіряє чинну сесію **до** запиту до сервісу; довільного proxy немає.
6. Додати ліміт тіла 32 KiB / 20 подій, перевірку Origin для публічного шлюзу, початковий rate limit 60 batch-запитів/хв на мережеве джерело в одному процесі. IP використовується лише короткочасно для ліміту, не пишеться в analytics. Це обмеження зловживань, не доказ справжності кліку.
7. Підготувати прості команди міграції та очищення: raw-події старші 90 днів, запуск раз на добу штатним планувальником; окрема параметризована команда видалення історії за `product_id + visitor_id`. Без worker або таблиці завдань. На цьому кроці перевіряти лише синтетичні дані.

**Файли:** нові `services/analytics/`, `lib/analytics/contract.ts`, `lib/server/analytics-service-client.ts`, `app/api/public/analytics/events/route.ts`; зміни `compose.yml` і необхідних build/test-конфігурацій. Міграції — лише в `services/analytics/db/migrations/`.

**Не входить:** нові таблиці в БД контактів, materialized views, агрегати, експортери ботів, production-міграції.

**Готово, коли:** синтетична подія проходить API → PostgreSQL → читання сесії; повтор не змінює count; перезапуск зберігає дані; чужий product, публічний `form_success`, зайві поля, завелике тіло та запит без належного доступу відхиляються. Недоступна БД повертає помилку, не успіх. Очищення не зачіпає інші сховища.

### Крок 3. Довести основні події браузера до БД

**Робимо:**

1. Замінити поточну поведінку consent: до згоди не створювати analytics IDs, не накопичувати події в пам’яті, не надсилати їх пізніше. Зберігати лише рішення про згоду окремо від tracking.
2. Додати постійний пункт налаштувань аналітики у footer: дозволити/відмовити/відкликати. Відкликання очищає чергу й IDs та зупиняє збір у всіх вкладках. Оновити текст на чинній privacy-сторінці під фактичний збір.
3. Реалізувати visitor/session/page-view IDs і timeout за правилами розділу 5. Відмова браузерного сховища не повинна ламати сайт.
4. Надсилати `session_start`, `page_view`, `page_leave`; чинні Telegram-дії спрямувати в канонічний `element_click`. Саме тут усувається перший розрив між `trackEvent()` та БД.
5. Один transport: `fetch` із відповіддю сервера; batch до 20 подій / 32 KiB, flush раз на 10 секунд і після важливої дії. Черга лише в пам’яті: до 100 подій, TTL 5 хвилин, не більше трьох повторів із затримками 1/5/15 секунд. Повтори тільки при мережевій помилці, 429 або 5xx, із тим самим `event_id`. На hidden/pagehide — остання спроба через beacon; його результат не вважати підтвердженням запису.
6. Старий API залишити для старих клієнтів; новий provider пише лише в новий API. Не дублювати один новий перегляд у дві БД. Для локального перемикання передбачити один режим `legacy/new/off`.

**Файли:** `app/analytics-provider.tsx`, `lib/analytics.ts`, `lib/public-analytics-client.ts`; невеликі модулі identity/session/transport у `lib/analytics/`; footer і `app/(public)/privacy/page.tsx`; наявні analytics-тести.

**Не входить:** довготривала offline-черга, відновлення поведінки до згоди, збір Admin-дій.

**Готово, коли:** у браузері після згоди перегляд і Telegram-клік видно в новій БД з однією сесією; при pending/deny/revoke немає збору; reload, SPA, back/forward, повтор запиту та блокування storage не ламають сайт і не дублюють той самий перегляд. Analytics outage не блокує навігацію.

### Крок 4. Покрити важливі дії сайту

**Робимо:**

1. Додати `data-analytics-id` або явні виклики лише для головних CTA, меню, карток статей/проєктів, Telegram/YouTube, Amazon і завантаження APK. Використовувати стабільні IDs, не тексти DOM або довільні URL. Один фізичний клік має одного відповідального handler.
2. Додати impressions, scroll, оцінку активного часу й `article_read` за таблицею подій. Статичні сторінки не переводити цілком у client components.
3. Замапити чинні виклики: `hero_cta_click`, `channel_cta_click`, `quiz_teaser_cta_clicked` → `element_click`; `wizard_open` → `form_open`; `quiz_teaser_started/completed` → `quiz_started/completed`; `quiz_teaser_error` → `frontend_error` з кодом і компонентом quiz.
4. `quiz_teaser_question_answered` у v1 свідомо не зберігати в analytics; окремі відповіді не потрібні для початку/завершення. Кожна чинна назва повинна мати явне рішення «мапиться» або «поза v1», без мовчазної втрати потрібних подій.
5. Для student і partner додати `form_open/submit/error`. При submit передавати окремий необов’язковий analytics-контекст тільки за чинної згоди. Валідатор відокремлює його від даних заявки; у `contact_requests` цей контекст не записується. Збій або невалідність лише analytics-контексту не відхиляє справну заявку.
6. `form_success` створює Contact API після успішного збереження справжньої заявки, лише за дозволеного analytics-контексту; honeypot не створює подію. Сервер генерує окремий випадковий `conversion_id`, без ID заявки, email, імені чи тексту форми. Прибрати другий запис успіху через клієнтський `lead_submit_success`.
7. Надсилати server success однією спробою з timeout до 500 мс після commit заявки. Збій analytics не змінює успіх заявки; у технічний журнал потрапляє лише код збою доставки без payload та IDs. Outbox і publisher не додаємо.

**Файли:** чинні публічні компоненти CTA/меню/статей/книг/проєктів, `contact-wizard-student.tsx`, `contact-wizard-partner.tsx`, `quiz-teaser-daily-widget.tsx`; `app/api/contact/route.ts`, `lib/contact/contact-schema.ts`, `lib/server/contact-submission.ts`; невеликий серверний sender. Контактне сховище змінювати лише якщо потрібно явно відокремити analytics-контекст, без міграції його БД.

**Не входить:** кроки/значення полів, відповіді на питання, довільне стеження за DOM, гарантована доставка кожної конверсії.

**Готово, коли:** для кожного з 15 типів є сценарій із записом у БД; обидві форми, quiz, книги й Telegram перевірено. Одна успішна заявка створює один server success; honeypot і помилка контактної БД — жодного. При збої analytics заявка залишається доступною в чинному розділі заявок.

**Свідомий компроміс:** analytics показує доставлені підтверджені заявки спостережуваних сесій. Без outbox подія може загубитися при збої між двома БД. Повний операційний список усіх заявок — `/admin/deutschmit/requests`; його total не прирівнюємо до analytics-конверсій. Цю межу показуємо і в Conversions.

### Крок 5. Дати власнику Overview та Sessions

**Робимо:**

1. Створити `/admin/deutschmit/overview`, `/admin/deutschmit/sessions` і `/admin/deutschmit/sessions/[sessionId]`. `/admin/deutschmit` відкриває новий Overview; явний маршрут замінює Website-каркас без конфлікту з `[product]`.
2. Overview: відвідувачі, сесії, перегляди, Telegram-кліки, підтверджені analytics-заявки; денний графік і top pages. Періоди 7/30/90 днів. Показувати весь вибраний денний ряд, не лише останні сім рядків.
3. Sessions: початок і остання активність, перша/остання спостережувана сторінка, джерело, кількість переглядів, оцінка активного часу, результат. Пагінація по 50; фільтри період/сторінка/тип події.
4. Session Explorer: хронологічна стрічка «відкрив → scroll → активний час → клік → інша сторінка → Telegram/форма». Це список подій, без відеозапису чи Sankey. Деталі показують усю збережену сесію та явно позначають події поза вибраним періодом.
5. Запити проходять через явні захищені Next.js API handlers і `analytics-service-client`. SQL рахує raw events без проміжних таблиць. Кеш-ключі включають продукт і фільтри; відповіді `private, no-store`.
6. Показувати джерело «Website Analytics v2», початок доступної історії, UTC-період і час розрахунку. Loading, коректний нуль, відсутність спостережень, unavailable та застарілий snapshot мають різні стани. Помилку не перетворювати на `0`.
7. Зберегти `/admin/dashboard` та його API як «Стара статистика сайту» з окремим посиланням. Заявки й їхній архів залишити в меню Website. Нові та старі лічильники не підсумовувати.

**Файли:** нові сторінки у `app/(admin)/admin/(secure)/deutschmit/`, `app/api/admin/analytics/deutschmit/`; query-модулі сервісу, невеликі компоненти KPI/таблиці/timeline. Перевикористати наявні TanStack Query та Recharts.

**Не входить:** visitor-профілі, порівняння когорт, custom date ranges, Live, device-фільтри, нові адміністративні дії.

**Готово, коли:** контрольний сценарій із розділу 6 дає однакові числа у SQL, API та UI; видно послідовність реальної тестової сесії; після 30 хвилин бездіяльності стан визначається при читанні без worker. Старі метрики й функції доступні, а зупинка analytics показує помилку лише його розділу.

**Межа першого етапу:** після цього кроку вже можна відповідати, звідки прийшла сесія, що відкривала, на що натискала та чи доставлено підтвердження заявки. Це завершене ядро; додаткову інфраструктуру до нього не додаємо.

### Крок 6. Додати чотири прикладні звіти

| Сторінка | Що показує | Чого тут немає |
|---|---|---|
| `/admin/deutschmit/pages` | Перегляди/visitors за сторінкою, активний час, максимальний scroll, кількість `article_read`; перехід до сесій | CMS, окремого content registry у БД |

**Готово, коли:** кожен звіт використовує правила розділів 4–6, має перевірений контрольний приклад і веде до відповідних сесій; зміна фільтра не показує кеш попередньої вибірки як нові дані.

## 4. Фіксований контракт: 15 подій

Кожна подія має спільні поля з кроку 2. `event_id` — випадковий UUID, незмінний при retry; `received_at` і `source` задає сервер. `path` — лише відомий публічний маршрут або нормалізований шаблон, без query/hash. Невідомий шлях позначається `unknown`, його довільний текст не зберігається. `metadata` має окрему strict-схему за типом, довжини й числові межі; зайві поля відхиляються. Сервер приймає час не старший 5 хвилин і не далі 1 хвилини в майбутнє від приймання; відхилення годинника може спричинити пропуски, їх не приховуємо.

| № | Подія | Умова і мінімальні додаткові поля |
|---|---|---|
| 1 | `session_start` | Перша дія після згоди або timeout; entry path, зовнішній referrer host, очищені `utm_source / utm_medium / utm_campaign` за правилами нижче |
| 2 | `page_view` | Реально показана сторінка, новий `page_view_id`; prefetch/hash/accordion не створюють перегляд |
| 3 | `page_leave` | SPA-перехід або pagehide; причина, останні cumulative active ms і scroll. Доставка можлива з втратами |
| 4 | `element_impression` | ≥50% значущого елемента видно ≥1 с; один раз на element ID + placement + page view |
| 5 | `element_click` | Активація позначеного елемента; element ID, placement, destination із переліку: internal/telegram/youtube/amazon/download/other |
| 6 | `scroll_depth` | Вперше досягнуто 25/50/75/90% основного контенту; threshold, один раз за поріг/page view |
| 7 | `engagement` | Не частіше разу на 30 с за наявності нового активного часу; cumulative `active_ms` для page view |
| 8 | `article_read` | Один раз на article/page view: ≥60 с активного часу і ≥90% основного матеріалу; `article_id`, `rule_version=1`. Для згорнутих секцій потрібне фактичне відкриття/охоплення; scroll до footer сам по собі не достатній |
| 9 | `quiz_started` | Реально почато Website Quiz; `quiz_run_id`, quiz ID |
| 10 | `quiz_completed` | Завершено той самий run; `quiz_run_id`, answered count, correct count. Без текстів питань/відповідей |
| 11 | `form_open` | Відкрито форму; `form_id=student/partner`, випадковий `form_instance_id` |
| 12 | `form_submit` | Надіслано запит; form/instance ID, випадковий `submission_attempt_id` |
| 13 | `form_success` | Лише server: справжня заявка збережена; form/instance/attempt ID, server-generated `conversion_id`, дозволений session-контекст |
| 14 | `form_error` | Показана помилка validation/network/server; form/instance ID, attempt ID за наявності, фіксований `error_code`; без тексту помилки й значень полів |
| 15 | `frontend_error` | JS/unhandled або помилка quiz: фіксований код/тип і component ID; невідоме → `unknown_error`. Без довільного message/stack/body; до 5 подій на page view, без рекурсії через збій самого analytics |

`form_success` не дублюється клієнтською подією. На рівні producer та запитів також усуваємо семантичні повтори: page view за `page_view_id`, quiz complete за run ID, success за conversion ID, impression/scroll/article read за їхніми ключами. Реальні повторні кліки лишаються окремими подіями.

**UTM без попереднього списку кампаній:** нові значення `utm_source`, `utm_medium`, `utm_campaign` приймаються автоматично, якщо проходять однакове очищення у браузері та повторну серверну перевірку.

- Значення отримуємо через стандартний URL-парсер з одним декодуванням, нормалізуємо Unicode (NFKC), прибираємо крайні пробіли. Дозволені літери Unicode, цифри, звичайний пробіл, `.`, `_`, `-`; послідовності пробілів замінюємо одним `-`. Source/medium переводимо в нижній регістр; регістр campaign зберігаємо.
- Межі після нормалізації: source/medium — 1–64 символи, campaign — 1–128 символів; декодований вхід кожного поля — максимум 256 символів. Завеликі значення не обрізаємо, щоб різні кампанії не злилися в одну.
- До заміни пробілів відкидаємо значення з очевидними email, телефонними номерами, URL, HTML, керівними або іншими недозволеними символами. Небезпечні символи не видаляємо для перетворення приватного значення на прийнятну мітку; повторного URL-декодування немає. Сирі відхилені значення не передаємо з браузера й не записуємо в БД або логи.
- Відсутнє/порожнє поле лишається відсутнім; неприйнятне поле стає `unknown`, решта валідних UTM та сама подія зберігаються. Нова назва кампанії сама по собі не є причиною `unknown`.
- Контроль: `utm_source=Instagram&utm_medium=Paid%20Social&utm_campaign=Herbst%20Kurs%202026` → `instagram / paid-social / Herbst-Kurs-2026`, без запису кампанії в конфігурації. Перевірити також Unicode-назву, граничні довжини 64/128 та перевищення, email/телефон, URL/HTML, керівні символи й повторне кодування. UTM — загальні назви джерел і кампаній; дані окремої людини в них не підставляємо. Перевірка символів не гарантує розпізнавання всіх персональних даних.

Referrer зберігається тільки як зовнішній hostname. Паролі, cookies, IP, контактні дані, тексти форм, DOM, натиснуті клавіші й повні URL у події не потрапляють.

## 5. Сесії, час і чесні межі даних

- **Visitor** — випадковий ID цього браузера для Website, створений після згоди, з ротацією через 90 днів. Це не встановлена особа; ID Quiz Bank або Telegram не використовуємо.
- **Session v1** — послідовність активності **в одній вкладці**, із новим ID після 30 хвилин бездіяльності. Різні вкладки мають окремі сесії, спільний visitor; UI пояснює «сесія вкладки». Це свідоме спрощення без об’єднання паралельних timeline. Reload зберігає session ID; нова/дубльована вкладка починає іншу сесію — це окремий browser acceptance-сценарій.
- **Timeout** перевіряємо при наступній дії та при читанні сесії, без `session_end`, worker або scheduled finalization. Heartbeat прихованої/неактивної вкладки не продовжує сесію. Нова сесія на вже відкритій сторінці отримує `session_start` і новий `page_view`.
- **Page view** змінюється при реальному переході, reload і повторному показі через back/forward/BFCache; події видимості без нового показу не дублюють його. `sequence` задає браузерний порядок усередині сесії; для server success прив’язка через attempt ID, час commit і стабільний tie-breaker. Запізнілу подію показуємо за часом виникнення, а не надходження.
- **Active time** — приблизний час, коли вкладка видима, у фокусі й без idle понад 60 с. Перехід у hidden/blur зупиняє накопичення. Передаємо тільки лічильник часу; рухи/клавіші не зберігаємо. Для page view беремо максимум cumulative `active_ms` із engagement/page_leave, не суму heartbeat. У UI це «оцінка активного часу», а `article_read` — «ознака дочитування».
- **Entry/exit** — перша й остання спостережувані сторінки за збереженими подіями. Відсутність `page_leave` не доводить нульову тривалість. Відсутній start, пропуски sequence або обрізана retention історія позначаються неповними; немає спостережень про час → «немає даних».
- **Traffic** прив’язуємо до входу в сесію; внутрішня навігація його не перезаписує. Referrer/UTM повторюємо як невеликий дозволений session-контекст у подіях, щоб втрата `session_start` не втратила все джерело. Немає referrer/UTM → direct; невалідне або відхилене значення → unknown.
- **Періоди v1** — 7/30/90 календарних UTC-днів, включно із сьогоднішнім до `generated_at`: `[початок UTC-дня N−1 днів тому, generated_at)`. Фільтр за `occurred_at`. В UI явно UTC; часову зону Quiz Arena не змінюємо. Сесія, яка перетинає межу дня, може входити в обидва денні distinct, але лише один раз у period distinct.
- **Свіжість** — API повертає `generated_at`, `last_received_at` і межу доступної історії. Це не гарантія доставки всіх подій. Snapshot старший 5 хвилин позначається застарілим; ручне оновлення перераховує SQL. Порожній період за справного джерела відрізняється від ще не запущеного збору.
- **Охоплення** — лише спостережувані дії після згоди. Блокувальник, закриття вкладки, вичерпання черги чи збій сервісу можуть дати втрати. Відкликання зупиняє майбутній збір; видалення вже збереженої історії — окрема операція. Новий grant починає нові IDs без прихованого зв’язування.

## 6. Мінімальні формули та контрольний приклад

Джерело всіх нових чисел — `analytics_events` Analytics DB, `product_id=deutschmit`, тільки валідні збережені події. Спільні часові межі, фільтри, свіжість і пропуски визначено вище. Для списку сесій період відбирає session IDs з хоча б однією подією у вікні; деталізація може показувати всю доступну історію цих сесій. Усі частки показують чисельник/знаменник; при знаменнику 0 — «не визначено».

| Метрика | Формула |
|---|---|
| Visitors | `COUNT(DISTINCT visitor_id)` подій у вікні; period distinct не є сумою денних |
| Sessions | `COUNT(DISTINCT session_id)` подій у вікні; не count лише `session_start`, бо start може загубитися |
| Page views / page visitors | Distinct `page_view_id` серед `page_view`; visitors за тим самим path і вікном |
| Telegram clicks | Count `element_click` із `destination=telegram`; інші destinations рахуються окремо |
| Analytics-заявки | Distinct server `conversion_id` серед `form_success` у вікні; без загального total із контактної БД |
| Частка сесій із заявкою | Distinct sessions із server success у вікні / усі observed sessions у тому самому вікні ×100 |
| Active time сторінки | Max cumulative active ms для кожного її page view; середнє лише серед переглядів із виміром, поруч кількість виміряних. Для періоду — page views, що почалися в ньому; доступний підсумок цих views може дозбиратися пізніше |
| Scroll / article read | Max threshold на page view; distinct article/page-view pairs із `article_read`, без твердження про доведене читання |
| CTR елемента | Distinct page views із його impression і наступним click / distinct page views із його impression ×100; той самий element/placement і вікно. Кліки без зафіксованого impression показуються окремо |
| Traffic | Розбиття тих самих session IDs за entry referrer/UTM; conversion rate у кожній групі за тією самою формулою сесій |
| Forms / Quiz | Кількість open/submit/error за подіями; success за conversion ID; quiz start/complete distinct run ID. Послідовність показує timeline; співвідношення довільних totals не називаємо строгою воронкою |

**Обов’язковий набір синтетичних даних в одному UTC-дні:**

1. Visitor A, session A1, direct: `/` → `/wissen`. На `/wissen` active updates 30 і 60 с для одного page view; один impression Telegram CTA, потім один click цього самого CTA.
2. Visitor A, session A2, UTM campaign `test`: `/contact`, form open → submit → один server success після запису заявки.
3. Visitor B, session B1, direct: одна стаття з відкритим основним матеріалом, scroll 90%, active 60 с, один `article_read`, quiz start → complete.
4. Повторно надіслати той самий Telegram `event_id`, quiz complete і server success з незмінними IDs; у вже наявній A2 додати окремий honeypot-submit без success. Для CTR використати окремий позначений CTA з одним impression без click у B1.

Очікування: **2 visitors, 3 sessions, 4 page views, 1 Telegram click, 1 analytics-заявка, 1 завершений quiz, 1 ознака дочитування; частка сесій із заявкою 1/3 = 33,3%**. Active time `/wissen` — 60 с, не 90; direct має 2 sessions, campaign `test` — 1 session і 1 success. CTR натиснутого CTA — 1/1, іншого — 0/1. Дублікати не збільшують числа. Окремо перевірити повторний click як нову реальну дію, нульовий знаменник, межу доби/періоду, timeout і порожню/недоступну БД.

## 7. Legacy і момент завершення

- **Стара статистика сайту:** чинна `website_analytics_events` у БД сайту залишається доступною через старий dashboard/API з явним джерелом. Для неї немає session explorer; сесії зі старих даних не вигадуємо.
- **Quiz Arena:** чинні backend, БД, формули, адаптер, 2FA, метрики й дії залишаються. Старі залишки Website Analytics у backend бота позначаємо legacy в документації; новий importer, новий legacy API або перенесення історії не входять у v1. Уже доступний архів заявок зберігається.
- **Website v2:** окрема дата початку, нові IDs і БД; звіти не склеюють її uniques із legacy. Період до початку збору позначається недоступною історією, а не нульовим трафіком.

Задача реалізації завершена після кроку 8: власник бачить статистику сайту та шлях сесії, розуміє джерела/кліки/результати, і жоден чинний адміністративний доступ не втрачено. Після цього **зупиняємо розвиток у межах цього плану**. Нову інфраструктуру або звіти додаємо окремою задачею лише під конкретне запитання чи виміряну проблему.
