# Аудит останнього production-деплою — 2026-09-13

Область: deutschmit.de, підключення Quiz Arena, Website Analytics v2, доступ власника, збереження даних, резервування та відтворюваність останнього розгортання. Перевірки виконані після відновлення пароля та лічильників головної. Production-конфігурацію, дані, 2FA й поведінку збору в цьому аудиті не змінювали. Виконані авторизовані входи й читання агрегатів; секрети та вміст заявок не виводили.

Результат: останній деплой не можна вважати повністю прийнятим. Нижче відокремлені дефекти, незавершені вимоги та межі перевірки.

## Виявлені недоліки

1. **Історична статистика не підключена до правильного джерела в новому розділі.** Авторизований GET нового сайту `/api/admin/website-analytics/overview?days=90` повертає 0 переглядів, 0 відвідувачів, 0 Telegram-переходів. Він читає власну `website_analytics_events` у `deutschmit_site`, де SQL підтвердив 0 рядків. Старий авторизований API `https://deutchquizarena.de/api/admin/website-analytics/overview?days=90` повертає **193 / 5 / 3** відповідно. У старій `quiz_arena.website_events` збережено **234** рядки. Це не втрата записів, а неповне перенесення доступу до них. Попередні перевірки лише HTTP 200 не підтверджували правильність джерела. Потрібно підключити історичне джерело в UI, позначити його й перевірити значення, не змішуючи з v2.
2. **Пряме доручення збирати аналітику за замовчуванням не виконано.** Свіжий браузер показує діалог згоди; після переходів головною та контактом без вибору надіслано 0 analytics-запитів. Код provider також вимагає `consent === "granted"`. Privacy описує чинну opt-in поведінку. Її зміна лишається окремою незавершеною реалізацією; цей аудит її не впроваджував.
3. **Попереднє підтвердження 2FA було недоказовим.** Реальний вхід через новий шлюз і безпосередньо через старий API повертає `requires_2fa: false`. Сесія має `two_factor_verified: true`, хоча OTP у цьому сценарії не вводився. Це підтверджує вхід без окремого OTP-кроку, а не перевірену двофакторну автентифікацію. Причину та стан до деплою не встановлено. Аудит не вимикав і не обходив 2FA.
4. **Тестові дані залишилися у production-звітах.** Є одна нова заявка й одна серверна конверсія від погодженої тестової заявки `DEPLOYMENT TEST PR22`; збережено також тестове проходження quiz та помилки валідації тестового runner. Їх не можна трактувати як органічні результати відвідувачів. В аудиті нічого не видалено.
5. **Супровідні матеріали не відповідають чинній конфігурації.** `deploy/production/README.md` досі описує згенерований пароль та попередній email замість чинного owner override `/opt/quiz-arena-site/.env.owner`. Попередній rollout-report не враховує відновлення входу й виправлення головних лічильників. Серверний `operations.sha256` має розбіжності для `compose.yml`, `check-runtime.mjs`, `operate.sh` після цих змін. `restore-owner.py` у старому manifest не перелічений.
6. **Відтворюваність релізу незавершена.** `deploy/` та попередній production-report лишаються untracked у локальному Git. Образ frontend закріплений digest, але операційні файли доставлялись окремо; образ Analytics використовує локальний tag `deutschmit-analytics:sha-23b2a54`. Сам checkout main не відтворює всю чинну конфігурацію VPS.
7. **Резервування підготовлено, але повне відновлення не підтверджене.** Останні site/analytics dumps від 18:46 UTC пройшли SHA-256 і `pg_restore --list`. Таймер enabled/active, наступний запуск 2026-09-14 03:31:44 UTC; `LastTriggerUSec` і час запуску service порожні — автоматичного запуску ще не було. Копії є лише на тому самому VPS; restore rehearsal та повний rollback не виконувалися. Це межі підтвердження, а не доказ пошкодження backups.
8. **Заявлені 14 днів для журналів не підтверджені конфігурацією.** Privacy вказує 14 днів для server/proxy/security logs. Перевірені контейнери використовують Docker `json-file` з порожнім `LogConfig.Config`; у створеному Compose окремої політики ротації немає. Реалізацію саме 14-денного зберігання цих журналів не підтверджено. Ротація DB backups за 14 днів — інша політика.

## Що підтверджено

- Головні лічильники виправлені попередньою задачею: **502 користувачі / 27 869 завершених quiz**, звірені з Quiz Arena та браузером. До deployment check додана звірка чисел.
- Чинний owner login нового сайту працює. Через нього успішний Quiz Arena login, session, overview та читання архіву заявок. Це перевірка доступу, не аудит усіх адміністративних mutation.
- Нова БД сайту: **1 заявка**, **0 власних legacy-подій**. Стара БД: **1 архівна заявка**, **234 website-події**, **10 833 bot analytics-події** на час читання. Стару й нову заявки повертають різні авторизовані API; джерела не змішані.
- У Website Analytics: **102 події, 3 відвідувачі, 3 сесії**, **7 page_view**, **1 quiz_completed**, **1 form_success**. Шість звітів повертають HTTP 200 і дані, включно з Sessions, Pages, Events, Traffic, Conversions. SQL підтвердив 102 події та 3/3 унікальні visitor/session. Це поточний набір, що включає тести.
- Events v2 отримані між 2026-09-13 18:34:26.767784Z та 19:36:39.377862Z. Початок режиму new, за записом розгортання: 18:28:42.347562145Z; перша отримана подія й активація — різні моменти.
- Anonymous Analytics query повертає 401. Внутрішній Analytics health без ключа 401, з ключем 200. `/api/ready` та `/internal/health` публічно 404.
- Frontend, Analytics, обидві нові БД та старий backend здорові; перевірені контейнери без restart-loop. Migration-контейнер завершений, що відповідає його одноразовій ролі. Нові БД й Analytics не публікують порти хоста.

## Межі та наступний порядок

Аудит не виконував нових заявок, проходжень quiz, адміністративних mutation, міграцій, видалень, відновлення backups чи зміни збору. Повне відображення історичної статистики у старому frontend через браузер не підтверджене; правильний старий API перевірено. Пробний неавторитетний шлях `/admin/website-analytics` повернув 404 і не використаний як доказ поломки старого UI.

Пріоритет виправлень: правильне історичне джерело в новій адмінці; незавершений автоматичний збір; уточнення чинної 2FA; відокремлення тестових результатів; синхронізація runbook/manifest і фіксація операційної конфігурації в Git за дозволом; перевірене відновлення й зовнішня копія backups; узгодження фактичного зберігання журналів із privacy. Успішний HTTP-статус надалі не замінює перевірку даних та UI.
